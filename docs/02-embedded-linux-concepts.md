# 1단계: 임베디드 리눅스의 구조

Yocto를 배우기 전에 **"Yocto가 무엇을 만들어 내는가"** 를 알아야 합니다.
MCU 펌웨어는 `.bin` 하나지만, 임베디드 리눅스는 여러 조각으로 이루어져 있습니다.

---

## 1. 부팅 순서 (MCU와 비교)

**MCU:**
```
전원 ON → 리셋 벡터 → main() → while(1) { ... }
```

**임베디드 리눅스:**
```
전원 ON
  → ① ROM 부트코드 (칩 안에 고정, 수정 불가)
  → ② 부트로더 (U-Boot)          : DDR 초기화, 커널을 메모리로 로드
  → ③ 리눅스 커널 (zImage/Image)  : 하드웨어 드라이버 초기화
       + 디바이스 트리 (.dtb)     : "이 보드에 어떤 하드웨어가 어디 붙어있나" 정보
  → ④ 루트 파일시스템 (rootfs) 마운트
  → ⑤ init 프로세스 (systemd 또는 sysvinit/busybox init)
  → ⑥ 내 애플리케이션 실행
```

Yocto는 **② ~ ⑥ 전부를 소스에서 빌드**해서 SD카드/eMMC/플래시에 쓸 수 있는 이미지로 만들어 줍니다.

## 2. 각 구성 요소

### ② 부트로더 — U-Boot
- MCU의 부트로더와 비슷한 역할. 하지만 훨씬 큼 (네트워크, USB, 파일시스템 지원)
- 보드 시리얼 콘솔에서 부팅 직후 아무 키나 누르면 `=>` 프롬프트가 나옴
- Xilinx Zynq의 경우: `BOOT.BIN` = FSBL(1차 부트로더) + 비트스트림(FPGA) + U-Boot

### ③ 커널 + 디바이스 트리
- **커널**: 프로세스/메모리 관리, 드라이버. MCU의 HAL + RTOS 를 합친 거대한 버전
- **디바이스 트리(.dts → .dtb)**: 하드웨어 구성 설명 파일
  - MCU에서 `#define UART1_BASE 0x40011000` 처럼 하드코딩하던 걸, 별도 파일로 분리한 것
  - 같은 커널로 여러 보드를 지원할 수 있게 해 줌

```dts
/* 디바이스 트리 예시 (개념만) */
uart0: serial@e0000000 {
    compatible = "xlnx,xuartps";
    reg = <0xe0000000 0x1000>;   /* 주소, 크기 */
    interrupts = <0 27 4>;
};
```

### ④ 루트 파일시스템 (rootfs)
- 보드에서 `ls /` 했을 때 보이는 모든 것
- `/bin/ls`, `/lib/libc.so.6`, `/etc/` 설정, **그리고 내가 추가할 라이브러리 `/usr/lib/libxxx.so`**
- **"라이브러리를 추가한다" = rootfs에 .so 파일(+필요하면 헤더)을 넣는다** 는 뜻

## 3. 크로스 컴파일

MCU에서 `arm-none-eabi-gcc` 를 쓰는 것과 같은 개념입니다.

| | 컴파일러 예시 | 결과물이 도는 곳 |
|---|---|---|
| 네이티브 컴파일 | `gcc` (PC에서) | PC (x86_64) |
| 크로스 컴파일 (MCU) | `arm-none-eabi-gcc` | 베어메탈 ARM |
| 크로스 컴파일 (리눅스) | `aarch64-poky-linux-gcc` | ARM **리눅스** 위 |

리눅스용 크로스 컴파일에는 컴파일러 + **타겟 보드와 똑같은 버전의 라이브러리(sysroot)** 가 필요합니다.
PC의 `/usr/lib/libc.so` 가 아니라, 보드용 `libc.so` 와 링크해야 하니까요.

👉 Yocto는 이 **크로스 컴파일러 + sysroot 를 자동으로 만들어 줍니다.** 그리고 원하면 SDK로 뽑아서 배포할 수도 있습니다 (`bitbake -c populate_sdk`).

## 4. 라이브러리의 종류 (C 개발자라면 꼭 알기)

| 종류 | 파일 | 특징 |
|---|---|---|
| 정적 라이브러리 | `libfoo.a` | 실행 파일 안에 합쳐짐. MCU에서 쓰던 방식 |
| 공유(동적) 라이브러리 | `libfoo.so` | 실행 시 로드. 리눅스의 기본 방식. 여러 프로그램이 공유 |

### 공유 라이브러리, 쉽게 이해하기

**비유: 정적 = 책을 한 권씩 사서 각자 집에 두기 / 공유 = 도서관에 한 권만 두고 다 같이 빌려 보기**

MCU에서는 `printf` 를 쓰면 그 코드가 `firmware.bin` 안에 **복사되어 들어갔습니다** (정적).
리눅스에서는 `printf` 코드를 실행 파일에 넣지 않고, **"printf 는 libc.so 에 있음"이라는 메모만** 남깁니다.
프로그램을 실행하는 순간 리눅스가 그 메모를 보고 `/usr/lib/libc.so.6` 을 찾아 메모리에 붙여 줍니다.

```
[정적]  helloapp = 내 코드 + printf 코드 + hello() 코드     (혼자 다 들고 있음, 큼)

[공유]  helloapp = 내 코드 + "printf→libc.so.6, hello()→libhello.so.1 에서 가져올 것"
                                │                           │
               실행할 때 연결 ──┘ /usr/lib/libc.so.6        └─ /usr/lib/libhello.so.1
```

이렇게 하면 좋은 점:
- **용량 절약**: 프로그램 100개가 `libc` 를 써도 보드에는 `libc.so` 한 개만 있으면 됨
- **라이브러리만 교체 가능**: 라이브러리 버그를 고치면 `.so` 파일만 바꾸면 되고, 그걸 쓰는 프로그램은 다시 컴파일 안 해도 됨

대신 주의할 점:
- **실행 파일만 보드에 복사하면 안 될 수 있음.** 보드에 그 `.so` 가 없으면 실행할 때
  `error while loading shared libraries: libhello.so.1: cannot open shared object file` 에러가 납니다.
  → 그래서 Yocto 이미지에 라이브러리 패키지도 같이 넣어야 합니다.

### 파일이 왜 3개나 있나요?

라이브러리 하나를 설치하면 이름이 비슷한 파일이 여러 개 보입니다. 각자 **찾는 사람이 다릅니다.**

```
libfoo.so.1.2.3   ← 진짜 파일. 내용은 이것 하나뿐
libfoo.so.1       ← 바로가기(심볼릭 링크). "실행할 때" 프로그램이 찾는 이름  → 보드에 필요
libfoo.so         ← 바로가기(심볼릭 링크). "컴파일할 때" -lfoo 가 찾는 이름 → 개발용
foo.h             ← 헤더. "컴파일할 때" #include 가 찾는 파일              → 개발용
```

- **컴파일할 때** (`gcc main.c -lfoo`): 컴파일러는 `foo.h` 와 `libfoo.so` 를 찾습니다.
  그리고 실행 파일 안에 "나중에 `libfoo.so.1` 이 필요함" 이라고 적어 둡니다.
- **실행할 때** (보드에서 `./helloapp`): 리눅스는 적혀 있던 `libfoo.so.1` 을 찾아 연결합니다.
- `.1` 은 **호환 버전 번호**입니다. `1.2.3 → 1.2.4` 처럼 고쳐도 호환되면 `libfoo.so.1` 은 그대로라서
  프로그램을 다시 빌드할 필요가 없습니다. 호환이 깨지면 `libfoo.so.2` 로 바뀝니다.

Yocto는 이걸 자동으로 패키지로 나눕니다:
- `libfoo` 패키지 → `libfoo.so.1.2.3`, `libfoo.so.1` (**실행**에 필요한 것 → 보드 이미지에 넣음)
- `libfoo-dev` 패키지 → `libfoo.so`, `foo.h` (**컴파일**에 필요한 것 → SDK, 또는 이 라이브러리를 쓰는 다른 레시피 빌드할 때 사용)

그래서 보통 이미지에는 `libfoo` 만 넣고, `-dev` 는 SDK에 들어갑니다.

## 5. 보드에서 라이브러리 관련 명령어

나중에 보드에서 확인할 때 씁니다.

```bash
ls -l /usr/lib/libhello*     # 라이브러리 파일 존재 확인
ldd /usr/bin/helloapp        # 이 프로그램이 어떤 .so 를 쓰는지 (없으면 "not found")
cat /etc/os-release          # 어떤 배포판/버전인지
uname -a                     # 커널 버전, 아키텍처
```

PC에서 크로스 빌드 결과를 확인할 때:
```bash
file helloapp                # "ELF 64-bit LSB ... ARM aarch64" 처럼 아키텍처 확인
```

---

## ✅ 1단계 자가 점검

1. 임베디드 리눅스 부팅 순서를 ROM → ... → 앱 까지 말할 수 있다.
2. 디바이스 트리가 왜 필요한지 MCU 개발과 비교해 설명할 수 있다.
3. `libfoo.so.1` 과 `libfoo.so` 의 차이, 그리고 보드에 어떤 게 꼭 필요한지 안다.
4. "라이브러리를 보드에 추가한다" 가 구체적으로 rootfs의 어디에 무엇을 넣는 것인지 안다.
